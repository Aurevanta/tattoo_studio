# Task: The client manages their designs — names them, deletes them, starts one from another

## 1. Problem / requested change

The owner: «Quiero que el usuario pueda gestionar sus tatuajes ya hechos desde el estudio: eliminar
un diseño, renombrarlo y editarlo». «Tus diseños» listed every version of the account in one flat
list, and the only deletion was «Elimina tus datos», which erases everything. Asked, the owner chose
(INTENT, 2026-10-16): delete a version **and** a whole design; group the list by design; the default
name is the client's idea, shortened; a confirmation before deleting; besides opening a version to
change it, start a new design from it. Decision: ADR-0041.

## 2. Current behavior

- `VersionList` (`apps/web/src/components/wizard/DoneStep.tsx`) and the advanced panel numbered
  every version of the account: «Propuesta N · <instruction>». Evidence: OBSERVED.
- No version knows its design except through `edit.parentJobId` / `capture.parentJobId`, and
  versions share stored files: a re-placement keeps its parent's artwork, stencils and PDFs; a kept
  photo keeps all of it. Evidence: OBSERVED (`app/studio.py::reposition`, `_capture`).
- Deletion: `DELETE /studio/session` only (ADR-0023 §4). Evidence: OBSERVED.

## 3. Requirements

- **REQ-001 (jobs)**: every version belongs to a design, `jobs.family` (the first version's job id):
  a change (`enqueue` with `edit.parentJobId`) or a kept photo (`record(parent=…)`) joins its
  parent's design; anything else starts one. Rows stored before are backfilled at start-up, oldest
  first; a version whose parent is gone starts its own design.
- **REQ-002 (jobs)**: a design has a name: the client's (`design_names`, one line, ≤ 60 characters,
  empty = default) or else the idea's first sentence shortened to ~48 characters at a clause or word
  boundary. `get`, `history` and `record` serve `design: {id, name}`.
- **REQ-003 (contracts)**: `studio-status` gains an optional `design: {id, name}` (`id` 32 hex,
  `name` 1–60 characters). Additive.
- **REQ-004 (platform)**: `DELETE /studio/jobs/{id}` deletes one version, `DELETE
  /studio/designs/{family}` a whole design. Both erase every file no remaining version of the
  account uses — artwork first, then uploads not used by a remaining version nor by a consultation in
  progress — the vector of a physical design no remaining version shows, and the links to erased
  versions. Rows stay, emptied and `cancelled`, so the day's designs still count. A design with a
  version queued or running is refused with 409. Another account's design answers 404.
- **REQ-005 (platform)**: `PATCH /studio/designs/{family}` `{name}` renames (422 for an invalid
  name). `POST /studio/designs` `{fromJobId, idempotencyKey}` records a copy of that version as the
  first version of a new design named «<name> (copia)», without `edit` or `capture` (a kept photo's
  copy gets a notice that does not call it a photograph), at no cost against the daily limit,
  idempotent per key. «Elimina tus datos» also forgets the names.
- **REQ-006 (web)**: `/api/designs`: `PATCH {designId, name}`, `DELETE ?designId=|?jobId=` (exactly
  one), `POST {fromJobId, idempotencyKey}` (needs current consent; the worker's answer is validated
  against `studio-status`). Ids are checked before the worker is called.
- **REQ-007 (web)**: «Tus diseños» (`DesignLibrary`, in step 1, the done step and the advanced
  panel) shows one card per design — name and number of versions — expanding to its versions,
  «Versión N · <what>», numbered within the design. Each version opens, and offers «Diseño nuevo a
  partir de esta» and, when the design has more than one, «Eliminar versión». Each design offers
  «Renombrar» (inline field, Escape cancels) and «Eliminar diseño». Deleting asks in place what goes,
  that shared links stop opening, that it cannot be undone and that the day's count stays; the
  destructive answer is never under the pointer that asked, and «Cancelar» has the focus. Deleting
  the version on screen closes it; a copy opens.

## 4. Non-goals

- Undo of a deletion (ADR-0041 revisit condition).
- Changing a design other than through the result view's existing tools (changes, mockup editor,
  3D): «editar» is opening the version.
- FINDING-0005 (the vector table's key).

## 5. Acceptance criteria

- **AC-001**: versions of one design share `design.id`; another design has its own
  (`test_versions_of_one_design_share_it_and_its_name`).
- **AC-002**: the default name is the shortened idea (`jobs/tests/test_designs.py`).
- **AC-003**: rename, reject a 61-character or non-string name, refuse another account, reset with
  an empty name (`test_a_design_is_renamed_and_its_name_can_be_reset`).
- **AC-004**: deleting a parent version keeps every file its child shows, removes the parent's own
  skin view, keeps the design and its name, the child can still be changed, and the day's count is
  unchanged (`test_deleting_a_version_keeps_what_the_others_use`).
- **AC-005**: deleting a design removes its versions (including a kept photo), its files, its
  reference and vector, and leaves exactly the other design's files, reference and vector
  (`test_deleting_a_design_erases_every_version_file_and_link`).
- **AC-006**: a link to an erased version stops opening; a link to another design still opens (same
  test).
- **AC-007**: deletion is refused with 409 while a version is queued, and succeeds after
  (`test_a_design_being_changed_is_not_deleted`).
- **AC-008**: a copy is its own design, «Lobo (copia)», same stencil, no `edit`, idempotent, free, and
  survives the original's deletion; a kept photo's copy leaves the photo
  (`test_a_new_design_from_a_version_is_its_own_design`, `test_a_copy_of_a_kept_photo_leaves_the_photo_behind`).
- **AC-009**: a database from before is backfilled
  (`test_versions_stored_before_designs_existed_find_their_design`).
- **AC-010**: contract fixtures `with-design` (valid) and `design-without-name` (invalid) agree in
  both runtimes.
- **AC-011**: the web route sends the account as owner, checks ids, needs consent only to copy, and
  validates the copy (`api/designs/route.test.ts`); the list groups and labels
  (`lib/designs.test.ts`, `DesignLibrary.test.tsx`).
- **AC-012**: in a browser, rename, copy, delete a version and delete a design work end to end.

## 6. Decision log

- **DEC-001**: the design is a stored column, not derived from `parentJobId` at read time, because
  deleting a version would otherwise split its children off (ADR-0041 §1).
- **DEC-002**: files are erased by reference counting over the account's remaining versions rather
  than by `delete_cascade` from the version's uploads, because versions share files and a cascade
  from a reference reaches every design made from it.
- **DEC-003**: rows are emptied, not deleted, so deleting cannot refund the daily limit.
- **DEC-004**: the confirmation is in place, inside the card, not a second dialog: the list already
  sits inside a dialog (`Confirm belowHeader`), and stacking them would fight over inertness and
  Escape.
- **DEC-005**: found in the browser check — the first layout put «Eliminar diseño» (destructive)
  exactly where the «Eliminar diseño» that opened it was, so a double click would confirm. «Cancelar»
  now takes that place and the focus.
